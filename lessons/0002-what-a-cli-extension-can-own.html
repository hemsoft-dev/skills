What a CLI extension can own

The useful unit is a session participant with memory and Node.js behind it.

The design test. Use an extension when behavior depends on what happens during a live session. Use a skill for instructions and MCP for an external tool service.

Five solid capabilities

Capability What it buys you Example
Model-callable tools A JSON-Schema function whose result goes back into the model's context. release_readiness gathers checks that the built-in tools do not expose as one answer.
User slash commands A deterministic action that bypasses model tool selection. /sessionstats prints tool count, failures, duration, and token use.
Events and memory The process observes activity and keeps state across turns. Pair tool.execution_start with tool.execution_complete to measure every tool call.
Terminal forms The host can collect a confirmation, selection, text value, or structured form. A release command asks for environment and version, then confirms production.
Local processes The extension can run Node.js code and use supported shell execution RPCs. Start a dev server, stream its logs, report health, and stop it cleanly.

GitHub's official tutorial proves the first three with a tool-time observer and a token-count command. The Node SDK reference documents capability-gated UI elicitation. The CLI changelog records session.shell.exec and session.shell.kill.

A small but real extension

This one process observes failures, answers a model tool call, and handles a user command:

import { joinSession } from "@github/copilot-sdk/extension";

let failures = 0;

const session = await joinSession({
  tools: [{
    name: "session_failure_count",
    description: "Report failed tool calls in this session.",
    parameters: { type: "object", properties: {} },
    handler: async () => `${failures} tool calls have failed.`,
  }],
  commands: [{
    name: "failures",
    description: "Print the current failed tool-call count.",
    handler: async () => {
      await session.log(`${failures} tool calls have failed.`);
    },
  }],
});

session.on("tool.execution_complete", (event) => {
  if (event.data?.success === false) failures += 1;
});

The model may call session_failure_count. The human may run /failures. Both read the same module state.

Examples worth building

Session flight recorder Count tool calls, correlate durations and failures, track usage, then expose /sessionstats and a model-callable diagnostic tool.
PR review cockpit Keep the selected PR in session state, gather current-head checks and review threads, and ask for confirmation before any write-capable command.
Local model monitor Poll Ollama health, record model latency during the session, provide /localstatus, and let the user select a model through a terminal dialog.
Development process keeper Launch a server or benchmark, stream output, retain the process identifier, and stop it through a command or tool.
Release guardian Accumulate evidence while the agent works, expose one readiness result, then require an explicit human confirmation before a release action.

Where Canvas enters

The same extension locations also hold Canvas extensions for the Copilot app. The app adds the missing visual host: a shared side-panel artifact that people edit while the agent calls its capabilities. GitHub documents /create-canvas as the supported creation path, but it does not yet publish a stable free-form Canvas API reference.

That suggests a clean split. Put session observation, commands, and local process control in the executable extension. Add a Canvas when the human needs a board, dashboard, document, or other visual state.

Two hard limits

Module state lasts only until the extension reloads or the session restarts. Persist anything important yourself. More seriously, the extension runs as local JavaScript with your operating-system privileges. Load Only prevents Copilot from rewriting extensions, but it does not sandbox code you chose to load.
